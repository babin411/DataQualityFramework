    What to monitor¶

    In the 1:1, you asked where the Snowflake tables are in the UW architecture. The deployment work starts from the config tables, but the diagram shows no table for the request data. The manager's answer settles which tables input monitoring actually reads.

    Not the config tables¶

    The config tables hold reference data: thresholds, MCC statistics, lookup values. They change rarely, through a governed admin console. They are not what data quality monitoring tracks.

    Config tables still need some care

    The support guide notes that an empty or malformed config file can break every request. That is an operational check: did the config pipe run, is the S3 file valid. It belongs with deployment and support, not in the DQ input reports.

    Auto-decisioned vs manually reviewed applications¶

    The manager also explained a second kind of table, which the stand-in table belongs to.

    flowchart TB
    APP["Application arrives<br/>(API request)"] --> MODEL{"Model + rules<br/>can decide?"}
    MODEL -- "yes (~80%)" --> AUTO["<b>Auto-decision</b><br/>approve or decline in real time<br/><i>locked: never changes afterwards</i>"]:::auto
    MODEL -- "no (~20%)" --> MAN["<b>Manual review</b><br/>routed to the underwriting team"]:::man
    MAN --> S1["Pending"] --> S2["In review"] --> S3["Approved / declined"]
    AUTO --> T1[("Request + output tables<br/>one row, point in time")]:::auto
    S3 --> T2[("<b>Manual-review status table</b><br/>status changes over time")]:::man

    classDef auto fill:#127EA6,stroke:#0b5a78,color:#fff;
    classDef man fill:#BC5618,stroke:#8a3e10,color:#fff;
    Auto-decision Manual review
    Share of applications ~80% ~20% (the share that "goes for manual review")
    When decided Real time, inside the API call Later, by an underwriting analyst
    Does the record change? No. Locked at the point of decision Yes. Status moves over time until approved or declined
    Where it's stored Request table (input) + 5c output A separate status table

    The status table complements the auto-decision data. Without it, monitoring sees only the applications the model decided. It still matters to track, so it isn't throwaway work.

    Choosing the 10 variables¶

    Simplified in the check-in

    You don't need to find the important columns first. "Take a few columns" and write one check of each type with tight criteria. See the test plan.

    Pick variables that exercise every check type in the template, so the MVP proves the whole parser, not just one rule.

    Pick at least one… Exercises Likely candidate (inferred)
    Status field (categorical) Accepted Values; new-value detection Final status
    Timestamp Freshness (is the table still updating?); Expected Format Last-updated / decision date
    Application or merchant ID Duplicate Values; Value Length; Expected Format Application ID
    Amount (numeric) Acceptable Range; Placeholder Value (-999) Requested amount / average ticket
    Often-empty field Missing Values; Field Population Analyst comments / reason code
    Field used by a model or rule Proves the "monitor what matters" rule Any score or bureau field present

    Watch the 15-minute refresh

    A table that updates in place (status changes) behaves differently from an append-only log. - Volume checks should count rows changed in the window (by a last-updated timestamp), not rows created. - Duplicate checks must use the table's key (for example application ID + status timestamp), or every status change looks like a duplicate. - Expect up to a 15-minute lag. Run the hourly checks a little after the hour (for example at :20) and check the previous full hour.
