    After the BRD: overview¶

    This section covers a 1:1 with the manager held the day after the BRD walkthrough. The meeting answers the question "the BRD is written, what happens now?" It turns the proposal into concrete next steps: who to email, what ticket to raise, which table to build on, what the reports must look like, and how the hourly alerts get sent.

    Source and labels

    This section is based on an automatic speech-to-text transcript, which garbles names and table names. Spellings I'm unsure of are marked (spelling uncertain). Anything I've worked out rather than heard is marked (inferred). See Transcript corrections.

    The meeting in one paragraph¶

    The team has a lot of model deployments in the next ~45 days, and deployments remain the priority for the next couple of weeks. Monitoring continues in parallel. On monitoring, the manager wants three things now:

    1. Socialise the BRD. Send the two templates to everyone and raise a Jira ticket so the modelling team fills them in for the new Underwriting models.
    2. Don't wait for them. Build the whole thing end to end on a stand-in table that already refreshes every 15 minutes.
    3. Make it real. Turn the filled-in Excel template into running checks. Produce clean, fixed-layout reports, and send hourly email alerts from AWS (Lambda + SNS).

    The first review is on Friday, 12:30–1:00 pm.

    Updated by the Implementation Support Document

    The model team's implementation document for UW US V2 gives the go-live dates (A1: 15 October 2026, A2: January 2027), names the Day 1 Snowflake tables, and links a field mapping sheet the comparison checks need. See Implementation Support Document.

    Updated by a stakeholder email

    An email from Michelle Davis sets the first focus (the A2 input, from January; A1 today) and adds two requirements: compare raw data with the payload, and alert when a dataset gets no activity. See Requirements update.

    Updated by a later check-in

    A follow-up conversation changed how to ask for the templates, added a test plan for the alerting, and set a target: fully automated in about three weeks. See Check-in: templates, test plan & timeline.

    Deployment context¶

    The first part of the 1:1 was about deployments. It explains why monitoring is "in parallel" rather than the main job for now.

    • Upcoming work in ~45 days: the lift-and-shift model, a new EWS solution, new models, and GNF. The manager is worried about becoming a bottleneck.
    • Primitive models: you have already deployed, merged and tested them, including checking the outputs on AWS. The composite models come next (RN is finishing other work first).
    • Learning goal: shadow Amok and Austin on every deployment. The aim is to deploy with RN alone if both are out, "not day one, but pretty soon". Long term, everyone should deploy and support both real-time and batch.
    • Branching, as the manager understands it (confirm with Amok):
    flowchart LR
    DEV["Developer<br/>feature work"] -- "merge request" --> STG["<b>staging</b><br/>(treated as the feature branch;<br/>stays here through cert)"]
    STG -- "deployment team adds CI/CD<br/>changes, merges at prod" --> MAIN["<b>main</b><br/>(production only)"]

    Developers merge into staging. The deployment team handles staging → main, adding what CI/CD needs before the merge. While a model is in cert, it stays in staging; main is only touched for production.
