    Before the config tables¶

    The architecture diagram starts at Snowflake Config Tables. The transcript answers the question "what is upstream of those tables?"

    Short answer¶

    For the true config tables, nothing technical is upstream except people's decisions. They are parameters for the service: mappings, categories and lookups that the models and rules need. They are entered through a governed admin console UI, not produced by a data pipeline.

    flowchart LR
    A["Analysis / business decision<br/>(e.g. 'map TMX codes differently')"] --> B["Admin console UI<br/>(new MRV / visual app)"]
    B -- "one row at a time,<br/>approved & decisioned" --> C[("Snowflake<br/>config tables")]
    M["Underwriting developers'<br/>upstream processes (unclear)"] -.-> D[("Monthly batch tables<br/>MCC-level stats")]
    C --> E["SF2AWS Config Table Pipe Lambda"]
    D --> E
    E --> F[("S3 reference cache")]

    Step by step¶

    1. Someone identifies a need for config¶

    Example from the transcript: a data scientist (Arjen) identified that three new config tables were needed for multiple models. The modelling team supplies the "starting place for the data", and the engineering team puts it into Snowflake.

    2. Config is defined in the admin console¶

    In the admin console of the new app, each true config table is a governed key/value view. The example shown was TMX code categories:

    key value
    a TMX code the category it maps to

    Properties called out in the meeting:

    • Governed: rows are approved and decisioned.
    • One row at a time: you cannot bulk-update with a Snowflake process; each change is an ad-hoc, deliberate edit.
    • Relatively static: changes over time, but not on a regular schedule.
    • Work in progress: Sachin has been setting many of these up; most are still empty and need to be populated.

    3. The tables live in Snowflake¶

    Today the tables sit in a config schema in Snowflake. Over time they will migrate to the UI-governed style (like TMX code categories).

    4. Monthly batch tables (missing from the diagram)¶

    The diagram only shows "config tables", but there is a second category:

    • Monthly batch tables holding MCC-level statistics (MCC = Merchant Category Code).
    • These do have something upstream, owned by the underwriting developers; the full picture was not known in the meeting.
    • For now they may be updated manually; a proper deployed process is planned later.

    5. Cache to S3 (the "yellow dotted line")¶

    The team's concern is simply: whatever is in Snowflake must be cached to S3. That is done by the SF2AWS Config Table Pipe Lambda using a state file.

    How the caching job decides what to refresh¶

    sequenceDiagram
    participant L as SF2AWS Config Lambda
    participant St as State file
    participant SF as Snowflake
    participant S3 as S3 reference bucket
    L->>St: read rows (one per table / S3 file)
    loop for each row
        L->>SF: run the SQL in the row's "query" column
        SF-->>L: result set
        L->>L: hash result -> new fingerprint
        alt fingerprint changed
            L->>S3: write/overwrite the cached file
            L->>St: store new fingerprint
        else unchanged
            L->>L: skip (no write)
        end
    end
    • Each row of the state file corresponds to one file that lands in S3.
    • The row has a query column (the SQL to run) and a fingerprint (hash of the last result).
    • Because config changes rarely, most runs are no-ops; S3 is only rewritten when the data really changed.

    Why this matters for support

    If a config change made in the UI does not show up in decisions, the chain to check is: UI row approved → Snowflake table updated → Lambda ran → fingerprint changed → S3 file updated → state machine reading the new file. See the support guide.
